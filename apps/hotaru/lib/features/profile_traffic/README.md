# Profile traffic

`ProfileTrafficRecorder` observes an existing sing-box lifecycle. It never starts, stops or selects a core. The application facade owns one recorder per core and closes the core before disposing the recorder. Live samples use the committed configuration/session; final samples use the immutable profile identity carried by the owned lease, including a short-lived running event delivered after the state has moved on.

The host's clean stopped receipt carries final cumulative counters after engine cleanup. Final counters are exposed only after the private control stream drains and EOF confirms the receipt. An unclean/missing receipt reports unavailable final data instead of inventing zero traffic. SQLite stores absolute checkpoints per core session and adds only their positive deltas to the owning profile. Duplicate, reordered and late final samples do not recount previous sessions or use a newly selected profile's identity. Writes and checkpoints commit in the same transaction; failed writes can recover from a later absolute sample.

Call `ProfileTrafficDao.initialize` when importing a new supported profile. It creates zero totals without resetting existing observations. Do not backfill an older profile's unknown historical usage or substitute its subscription quota. Schema 23 extends the same unshipped migration as the IP facts cache and preserves existing data. Removing a profile deletes its totals/checkpoints through foreign keys. The profile card shows a compact localized total only when an observed/initialized row exists, independently of provider quota data; it does not grow the card.

The ordinary application facade is still being migrated. This module's controlled tests exercise actual persistence and lifecycle binding; completing the normal GUI source selection remains necessary before release. Upstream closed-connection snapshots are not used as cumulative totals, because their bounded window can be evicted or cleared by GC.
